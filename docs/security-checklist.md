[Architecture §10.1](architecture.md#101-threats-and-controls) requires a
written security checklist that must pass before the first public deployment
of `shinan.guneet.dev`, and again before the `workspace` repository's catalog
moves over. This is that checklist. It covers the threats and controls in
[architecture §10](architecture.md#10-security), the observability rules in
[§13](architecture.md#13-observability) that affect exposure, and the
protections for a public installation in
[identity §10](identity.md#10-protections-for-a-public-installation). Those
documents own the rules; this one only checks them.

## How to use it

- Each item says how it is checked: a test (which runs in CI on every pull
  request), a command, or a reading of the code or configuration.
- Results:
  - **Pass**: true of the code today.
  - **Fail**: not true today; the item says what is needed and who does it.
  - **Deployment**: depends on how Shinan is deployed; checked when the
    deployment is prepared ([M1-7](https://github.com/guneet-xyz/shinan/issues/59))
    and again at the deployment approval.
  - **Later**: the feature is not built yet. The package that builds it adds
    the check, and the item must pass before that feature is deployed.
- Before the first public deployment, every item must be **Pass**, or
  **Deployment** with the deployment's evidence, or **Later**. Before the
  catalog moves over, run the whole list again, including the **Later** items
  built by then.
- When a change alters a result, the same pull request updates this document.

### The application's database role (6.7)

**Finding** (from the review of
[#132](https://github.com/guneet-xyz/shinan/pull/132)): the security log,
events, revision text and purge records are append-only because database
triggers refuse other changes (6.2, 6.5). But `web`, `worker` and `migrate`
all connect as `shinan`, which owns every table and, as the PostgreSQL
image's `POSTGRES_USER`, is a superuser. That role can turn the triggers off
(`ALTER TABLE … DISABLE TRIGGER`), skip them with no DDL at all
(`SET session_replication_role = replica`), or do anything else in the
database server. The triggers stop Shinan's own code from rewriting history
by mistake; they don't stop someone who has taken over the `web` or `worker`
process.

What such an attacker gains either way: they already hold the session
secret, the database password and every row. The role decides only whether
they can also rewrite the record of what they did, and (as a superuser)
reach the database container itself, for example with `COPY … TO PROGRAM`.
Shinan builds every query with parameters (Drizzle), the database is on an
internal network with no port published, and nothing known lets a request
run SQL of its choosing.

**Option A: a non-owner role for the app, now** (not chosen).

- `migrate` keeps connecting as `shinan`, which owns the tables. `web` and
  `worker` connect as a new role, such as `shinan_app`, that may read and
  write rows but owns nothing and is not a superuser. The triggers then
  hold even against a compromised `web`.
- Work in Shinan: grants and default privileges for later tables;
  `CREATE` on pg-boss's schema, since pg-boss 12's `createQueue`, which the
  worker calls when it starts, creates a partition table per queue;
  `MAINTAIN` on the tables purge vacuums (PostgreSQL 17 and later); tests
  that run as the app role; the reference Compose file and the operator
  guide.
- Deployment change on Musashi's stack: a second database role, its
  password as a new secret in the `shinan` Obscuro namespace, a second
  `DATABASE_URL` for `web` and `worker`, with the owner's approval.

**Option B: accept the risk for v0.3.0, with a follow-up** (chosen).

- 6.7 is an accepted risk (as 9.3 is), and option A is done first in M3,
  before git host credentials or a second member's data are stored.
- Nothing changes on Musashi now.

Reasons, as recommended and recorded in D-057: the risk is to audit
integrity after a full compromise of the `web` process, which already gives
the attacker every row, and opens no new way in; the trial has one member
and a small catalog, and Musashi's database is unreachable from outside;
and option A touches pg-boss's runtime schema, purge's vacuum, the
reference Compose file and a new secret on Musashi, a larger risk to the
deployment under release pressure than the one it removes.
