[Architecture §10.1](architecture.md#101-threats-and-controls) requires a
written security checklist that must pass before the first public deployment
of `shinan.guneet.dev`, and again before the `workspace` repository's catalog
moves over. This is that checklist. It covers the threats and controls in
[architecture §10](architecture.md#10-security), the observability rules in
[§13](architecture.md#13-observability) that affect exposure, and the
protections for a public installation in
[identity §10](identity.md#10-protections-for-a-public-installation). Those
documents own the rules; this one only checks them.

## How to use it

- Each item says how it is checked: a test (which runs in CI on every pull
  request), a command, or a reading of the code or configuration.
- Results:
  - **Pass**: true of the code today.
  - **Fail**: not true today; the item says what is needed and who does it.
  - **Deployment**: depends on how Shinan is deployed; checked when the
    deployment is prepared ([M1-7](https://github.com/guneet-xyz/shinan/issues/59))
    and again at the deployment approval.
  - **Later**: the feature is not built yet. The package that builds it adds
    the check, and the item must pass before that feature is deployed.
- Before the first public deployment, every item must be **Pass**, or
  **Deployment** with the deployment's evidence, or **Later**. Before the
  catalog moves over, run the whole list again, including the **Later** items
  built by then.
- When a change alters a result, the same pull request updates this document.

### The application's database role (6.7)

**Finding** (from the review of
[#132](https://github.com/guneet-xyz/shinan/pull/132)): the security log,
events, revision text and purge records are append-only because database
triggers refuse other changes (6.2, 6.5). But `web`, `worker` and `migrate`
all connect as `shinan`, which owns every table and, as the PostgreSQL
image's `POSTGRES_USER`, is a superuser. That role can turn the triggers off
(`ALTER TABLE … DISABLE TRIGGER`), skip them with no DDL at all
(`SET session_replication_role = replica`), or do anything else in the
database server. The triggers stop Shinan's own code from rewriting history
by mistake; they don't stop someone who has taken over the `web` or `worker`
process.

What such an attacker gains either way: they already hold the session
secret, the database password and every row. The role decides only whether
they can also rewrite the record of what they did, and (as a superuser)
reach the database container itself, for example with `COPY … TO PROGRAM`.
Shinan builds every query with parameters (Drizzle), the database is on an
internal network with no port published, and nothing known lets a request
run SQL of its choosing.

**Option A: a non-owner role for the app, now** (not chosen).

- `migrate` keeps connecting as `shinan`, which owns the tables. `web` and
  `worker` connect as a new role, such as `shinan_app`, that may read and
  write rows but owns nothing and is not a superuser. The triggers then
  hold even against a compromised `web`.
- Work in Shinan: grants and default privileges for later tables;
  `CREATE` on pg-boss's schema, since pg-boss 12's `createQueue`, which the
  worker calls when it starts, creates a partition table per queue;
  `MAINTAIN` on the tables purge vacuums (PostgreSQL 17 and later); tests
  that run as the app role; the reference Compose file and the operator
  guide.
- Deployment change on Musashi's stack: a second database role, its
  password as a new secret in the `shinan` Obscuro namespace, a second
  `DATABASE_URL` for `web` and `worker`, with the owner's approval.

**Option B: accept the risk for v0.3.0, with a follow-up** (chosen).

- 6.7 is an accepted risk (as 9.3 is), and option A is done first in M3,
  before git host credentials or a second member's data are stored.
- Nothing changes on Musashi now.

Reasons, as recommended and recorded in D-057: the risk is to audit
integrity after a full compromise of the `web` process, which already gives
the attacker every row, and opens no new way in; the trial has one member
and a small catalog, and Musashi's database is unreachable from outside;
and option A touches pg-boss's runtime schema, purge's vacuum, the
reference Compose file and a new secret on Musashi, a larger risk to the
deployment under release pressure than the one it removes.

**Accepted for v0.4.0, with reasons** (the open items of #173's lists and

- **`web` holds the Git service token** (D-065): a compromised `web` could
  send the Git container any context. It already holds the database and
  every row; the Git container gives it nothing more. Listed in
  [architecture §10.1](architecture.md#101-threats-and-controls).
- **Commits no branch reaches stay readable by commit ID** through the Git
  container's read API until the pruner removes them: 20 seconds to 10
  minutes after pushes go quiet, an hour after a pruning that failed, or
  for good on a history whose whole repack never fits in memory (#208).
  Only `web` reaches that API, for commits it was given; the members who
  could ask had the branch anyway; purged text is never among them, since
  a purge puts in a new repository. Refusing such commits is
  [#215](https://github.com/guneet-xyz/shinan/issues/215). Listed in
  architecture §10.1.
- **Database dumps hold `catalog_ref_fingerprint_keys`**, so a dump's
  holder can confirm a guessed branch name offline. Dumps are written
  `umask 077` (the operator guide, and the deployment request's
  root-only `/var/lib/infra/shinan-deployments`); the step 1 dump of the
  v0.4.0 upgrade is a v0.3.0 dump, which holds none.
- **A purge's re-plan an agent can trigger** (taking a name the plan gave
  away runs the rewrite once more, about 75 seconds of held pushes on a
  20,000-page catalog): bounded to once per purge, and the operator guide
  says so.
- **The purge status** (`GET …/catalog/purges/:id`) is for the workspace's
  owners only (`catalog.purge-status`; `catalog-purge.test.ts`: 403 for a
  contributor), without signing in again. The list (`GET …/purges`) is for
  every member (`workspace.read`), with number, who, when, reason and
  counts, never text. The note in #173 that the status is for any member
  describes an earlier state.
- **In-flight places held after the Git deadline:** after a Git process is
  stopped at its 10 minutes, `web`'s places stay held until the client or
  Caddy closes the connection, bounded by the per-token and per-address
  caps.
- **One check of `main` at a time across workspaces** (see §2.10 above):
  recorded in the operator guide and plan §2.10.
- **The pruner after a deleted branch** held fetches at most 246 ms on the
  20,000-page catalog ([`4-load.log`](evidence/v0.4.0/4-load.log), "prune"); Musashi's
  catalogs are far smaller.
- **Compression:** not rated safe. Shinan's sign-in cookies are
  `SameSite=Lax`, so pages on other sites under the same domain count as
  the same site (`security.ts`, `sameOriginOnly`), and the origin check
  covers only requests that change something. So the operator guide says
  to leave compression off at the proxy, and Musashi's Caddy has no
  `encode` (D14). Shinan compresses only the catalog's tree itself, which
  holds the catalog's paths, titles and statuses, which every member reads
  anyway, and nothing from the request.
- **`/mcp`'s 512 KB body limit** stays (M2-Q16), though its one tool takes
  no input: the in-flight caps bound what slow senders hold, and M3's task
  tools will need room.
- **Git's words on protocol v2:** a `429` to a fetch's `POST` shows only
  `RPC failed; HTTP 429`; the skill tells agents what a 429 means.
- **`CatalogPurgePreview.counts`** keeps M2's fields: purges recorded under
  v0.3.0 stored real counts there, which the purge list still shows
  (explained in [#209](https://github.com/guneet-xyz/shinan/pull/209),
  which did the rest of GC-10's comment and name cleanup).

**A gap, not covered in v0.4.0: no recovery from agents' clones.** A lost
`catalog` volume comes back only from a backup taken with the database.
Recreating a repository from an agent's clone, as drafted in GC-11, could
bring back purged text (the list of removed commits is only on the
volume) and history that never passed the push checks, so the operator
guide does not describe it; a safe recovery is
[#216](https://github.com/guneet-xyz/shinan/issues/216). Musashi has no
backups (D-038), so there a lost `./catalog` is lost, apart from the copy
taken at the last deployment that changed it.

### Owner decisions for v0.4.0

The owner answered on 2026-11-28 (recorded on
[#173](https://github.com/guneet-xyz/shinan/issues/173#issuecomment-7239872729)):

- **6.7, the app's database role:** D-057 is **accepted again for v0.4.0**,
  the decision unchanged; #156 fixes it in M3.
- **`web`'s memory on Musashi:** **1,536 MiB stays**; GC-11's proposal of
  768 MiB is declined. `git` gets 1,024 MiB.
- **Very long histories: accepted for v0.4.0, relying on
  [#208](https://github.com/guneet-xyz/shinan/pull/208), which is therefore
  a release blocker: v0.4.0 must include it.** At 1,000,000 commits
  ([`5-long-history.log`](evidence/v0.4.0/5-long-history.log)): a page's History of a
  page changed once took 16 seconds; 12 at once took the Git container to
  its limit (5 Git processes stopped by the kernel, 5 reads answered 500,
  the container up); deep `history?skip=` reads stayed cheap (1.2 seconds at 299,900,
  3.7 at 999,999), so `maxHistorySkip` stays. The whole repack after a
  start or a deleted branch needs more than the container's memory. On
  `cfd8a8d`, the pruner's count then held about 850 MiB, and its failures
  were retried every minute, each holding the repository for minutes and
  leaving a ~400 MB file (the Git container restarted once). With #208,
  the stack logged one failure for the repository, "git repack exited with code 137:
  pack-objects ended by signal 9 (SIGKILL, often out of memory); tried
  again in 60 minutes", left no half-written pack, and tried no more after
  a deleted branch or a restart; a fetch meanwhile took 75 ms.
  Building such a history takes one agent hours at the push limits, every
  push in the push log. A cap on a repository's history can come later.
